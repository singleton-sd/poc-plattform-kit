# Shared support, diagnostics, and impersonation contract

Status: proposed discovery contract for implementation planning.

This vocabulary is normative across the three discovery ADRs and the roadmap.

| Term | Contract |
| --- | --- |
| `tenantId` | Immutable Platform Kit `Tenant.id`. It is not the Entra directory `tid`. Protected production requests derive it from verified membership, a server-side route resource, or an authorised server-issued impersonation session; they never trust a client-selected header as authority. |
| `authenticatedActor` | The local `User.id` mapped from the authenticated Entra/Auth.js principal. It never changes during impersonation. |
| `effectiveActor` | The local customer `User.id` selected by an authorised, server-side impersonation session. It equals `authenticatedActor` outside impersonation and never replaces it in audit or telemetry. |
| `impersonationSessionId` | Opaque server-issued identifier for a persisted, temporary, revocable session. A client cannot construct its tenant or effective identity. |
| `traceId` | W3C 16-byte trace identifier used by OpenTelemetry/Application Insights. It is operational metadata, not an authorisation capability. |
| `correlationId` | Public, opaque token generated by the API using a CSPRNG/ULID-equivalent with at least 128 bits of unpredictability (a standard RFC 4122 UUID does not qualify, since its version/variant bits reserve entropy below that threshold) and returned on responses. A server-side diagnostic index maps it to `traceId`; callers cannot force or reuse it as the authoritative value. |
| `errorCode` | Stable, namespaced, version-independent machine code such as `support.ticket_not_found`. HTTP status and human text may evolve without changing it. |

## Cross-cutting invariants

- Every protected request context preserves `tenantId`, `authenticatedActor`,
  `effectiveActor`, optional `impersonationSessionId`, `correlationId`, and
  `traceId` separately.
- Tenant and permission checks use the server-built request context. Client
  tenant headers, query parameters, user IDs, and local storage are not proof.
- Application Insights holds operational telemetry; append-only pillar audit
  records hold accountability. Neither replaces the other.
- Diagnostic records use explicit allowlists. They exclude request/response
  bodies, tokens, cookies, arbitrary headers, raw SQL, stack traces, secrets,
  and unrestricted PII.

## Verified contradictions requiring migration

1. `TenancyMiddleware` currently accepts `x-tenant-id` as a legacy/dev escape,
   and the generated-client configuration can set it. The target contract
   forbids using that value as authority for protected production operations.
   Phase 1 must replace it with verified membership/resource resolution and
   fail closed; local-only test tooling may use an explicit disabled-by-default
   adapter.
2. Correlation middleware currently accepts arbitrary inbound
   `x-correlation-id` or even the full `traceparent` value. The target contract
   generates a bounded public `correlationId` as defined above (CSPRNG/ULID
   equivalent, at least 128 bits of unpredictability) while preserving valid
   W3C propagation as a separate `traceId`.
3. The exception filter currently returns Nest's heterogeneous payload shape.
   The target contract is one versioned RFC 9457 representation and never
   exposes exception text or stack traces.
4. The browser telemetry helper can record a response-body snippet. The target
   allowlist prohibits response bodies, so that behaviour must be removed
   before diagnostic capture is enabled.
5. The OpenFGA guard currently maps only one tenant update route and bypasses
   fine-grained checks when OpenFGA is unconfigured. Support and impersonation
   endpoints must have explicit route mappings and fail closed in every shared
   environment.
